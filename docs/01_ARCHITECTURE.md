# 수학 학습 플랫폼 — 아키텍처 설계서

> 고등학교 수학 교사가 단독 운영하는 학습 플랫폼.
> 한 학년(~200명) 규모, 동시 접속 30~50명, 개인 부담 비용 최소화가 대전제.

---

## 0. 설계 원칙 (반드시 준수)

1. **교사 1인이 운영·유지보수 가능해야 한다.** 리눅스 서버 관리, nginx, 인증서 갱신, DB 백업을 직접 하지 않는 방향(관리형 서비스)으로 간다.
2. **AI 비용은 처음부터 통제한다.** 무제한 호출 금지. 학생별 일일 한도 + 캐싱을 스키마 단계부터 설계에 반영.
3. **직접 만들지 않아도 되는 것은 만들지 않는다.** 인증 → Supabase Auth, 그래프/도형 조작 → GeoGebra 임베드.
4. **MVP를 좁게.** 1단계는 "로그인 + 단원별 활동"만. AI 기능(챗봇/첨삭)은 인터페이스 자리만 잡고 2단계에서 붙인다.

---

## 1. 기술 스택

| 영역 | 선택 | 이유 |
|------|------|------|
| 프레임워크 | **Next.js (App Router, TypeScript)** | 프론트+백엔드 단일 코드베이스, API Route로 AI 호출 서버측 처리 |
| DB + 인증 | **Supabase (Postgres + Auth + RLS)** | 학반 회원/권한을 직접 구현 안 함. RLS로 "학생은 자기 데이터만" 자동 차단 |
| 배포 | **Vercel** | Next.js 무설정 배포. 이 규모는 무료~저가 티어로 충분 |
| 조작 SW | **GeoGebra 임베드** | 함수 그래프·도형 조작을 직접 만들지 않음 |
| AI (2단계) | **Claude API 기본 + GPT/Gemini 선택** | 소크라테스 질문·한국어 첨삭은 Claude가 우위 |
| 상태/UI | Tailwind CSS + 최소 컴포넌트 | 유지보수 단순화 |

### 로컬 AI (선택지, 비용 0 지향 시)
- **Qwen2.5-Math (7B)** — 수학 특화 오픈모델 중 최상위권, 한국어 무난. 24GB VRAM급 권장.
- **DeepSeek-Math / R1-distill** — 추론 강함.
- 주의: 소크라테스식 대화·한국어 첨삭 품질은 여전히 API가 우위. 상시 GPU 서버 관리 부담이 큼.
- **권장 경로**: 1단계는 활동만(AI 없음) → 2단계는 API로 시작 → 사용량 커지면 로컬 전환 검토.

---

## 2. 사용자 역할

- `student` : 자기 학년·반의 공개된 교과·단원·활동만 접근. 자기 진행기록만 조회.
- `teacher` : **자기가 만든 학생**의 계정·기록 관리, 교과·단원·활동 관리(교사 간 공유), 진도 확인.
- `admin`   : 교사 계정 관리, 전체 학생 조회, AI 키·모델·한도 설정. (`is_teacher()` 는 admin 도 참)

RLS 정책으로 DB 레벨에서 강제한다(프론트 검증만 믿지 않음).
단, `service_role` 은 RLS 를 우회하므로 **서버 API 에서 소유권을 따로 확인**해야 한다.

---

## 3. 로그인 방식 (확정)

**학번 + 초기비밀번호, 교사 배포 방식.**

- 이메일 수집 안 함 → 개인정보 최소화.
- 교사가 명단(학년/반/번호/이름)으로 계정을 **일괄 생성**하고 초기 비밀번호를 배포.
- Supabase Auth는 이메일이 필수이므로, 내부적으로 `{학번}@school.local` 형태의 **가상 이메일**을 학번으로 매핑해 생성한다(학생에겐 학번만 노출).
- 학생 최초 로그인 시 **비밀번호 변경 강제**.

## 4. 데이터 모델

```
profiles          -- auth.users 확장. 학년/반/번호/이름/역할/비번변경여부/담당교사(teacher_id)
subjects          -- 교과: 제목/학년/순서/공개여부              (0010에서 추가)
units             -- 단원: 교과소속(subject_id)/제목/학년/순서/공개여부
activities        -- 활동: 단원소속/유형/콘텐츠(JSON)/순서/공개여부/대상반
progress          -- 진행기록: 학생×활동, 완료여부/점수/제출내용/작성글(옛 방식)/타임스탬프
screen_responses  -- 화면별 기록: 학생×활동×화면키, 질문/글/사진경로  (0012에서 추가)
ai_usage          -- 학생별 일일 AI 호출 카운트 (비용 통제)
ai_conversations  -- 저장한 AI 대화 (학생당 최대 5개, 본인만 접근)
ai_secrets/models/limits/prompts -- AI 키·모델·한도·프롬프트 (관리자 설정)
```

계층은 **교과 → 단원 → 활동 → 진행기록** 이다.
학생에게 보이려면 교과·단원·활동이 **모두 공개**여야 한다(`unit_visible_to_me()` 가 이 규칙을 한 곳에 모은다).

`teacher_id` 는 **학생을 만든 교사**를 가리킨다(0011에서 추가).
교사는 자기 담당 학생만 조회·수정하고, 관리자는 전체를 본다.
반면 교과·단원·활동은 교사 간 **공유**된다 — 자료는 함께 쓰고 학생만 나눠 맡는 구조.

### activity 유형(`type`)
- `geogebra`   : GeoGebra 자료 ID를 임베드
- `content`    : 설명/자료 열람(HTML/마크다운)
- `problem`    : 문제 풀이(정답 제출·채점)
- `socratic`   : (2단계) 소크라테스 챗봇 활동
- `feedback`   : (2단계) 단계별 첨삭 활동

`content` 컬럼은 JSON으로 두어 유형별 필드를 유연하게 담는다.
예: geogebra → `{"materialId":"xxxx","height":600}` / problem → `{"question":"...","answer":"...","tolerance":0.01}`

## 5. 화면 구성 (MVP)

**학생**
- 로그인 → (최초 시 비번변경) → 대시보드(내 학반 단원 목록)
- 단원 클릭 → 활동 목록 → 활동 실행(GeoGebra / 문제풀이)
- 활동 완료 시 progress 기록

**교사**
- 관리 대시보드
- 학생 계정 일괄 생성(CSV 업로드: 학년,반,번호,이름)
- 단원 CRUD / 활동 CRUD(유형 선택, GeoGebra ID 입력 등)
- 학반별 진행현황 조회

---

## 6. 단계별 로드맵

- **1단계 (MVP)**: 인증 + 역할 + 단원/활동 CRUD + GeoGebra 임베드 + 문제풀이 + 진행기록. **AI 없음.**
- **2단계**: 소크라테스 챗봇 + 단계별 첨삭. `ai_usage` 기반 일일 한도, 응답 캐싱, 서버측 API Route로만 키 사용.
- **3단계**: 통계 대시보드(오답률·단원별 성취), 로컬 모델 옵션 검토.

---

## 7. 비용 통제 설계 (2단계 대비, 지금 스키마에 반영)

- 모든 AI 호출은 **서버측 API Route**에서만. API 키는 절대 클라이언트 노출 금지(Next.js 환경변수 `server-only`).
- `ai_usage(student_id, date, count)` — 학생당 일일 호출 상한(예: 20회). 초과 시 차단.
- 동일 문제·동일 풀이에 대한 응답 **캐싱**으로 중복 호출 절감.
- 모델 라우팅: 간단한 첨삭은 저가 모델, 복잡 추론만 상위 모델.

---

## 8. 보안·개인정보 체크리스트

- 이메일 미수집(가상 이메일). 최소 개인정보(이름/학반/번호)만.
- RLS로 학생 간 데이터 격리.
- 교사 계정은 별도 강력 비밀번호 + (가능하면) 2단계 인증.
- AI 대화 로그 보관 정책 명시(학생 데이터가 외부 API로 전송됨을 고지·동의 필요).
- 학교 방침에 따라 API로의 학생 데이터 전송 가능 여부를 사전 확인.
